# Assumptions

Each assumption can be changed; the ones marked **(data model)** are expensive to change later, so please confirm them.

| A2  | 26-11-2026 | **(data model)** One Tally company covers all the books.                                                                                                                                                                                                                                                                                            | 0     |
| A3  | 26-11-2026 | **(data model)** Project → Block (tower, wing or phase; optional) → cost code.                                                                                                                                                                                                                                                                      | 0     |

| A6  | 26-11-2026 | **(data model)** Stock is held per site (store location) and valued at weighted average cost.                                                                                                                                                                                                                                                       | 0     |

| A18 | 26-11-2026 | Placeholder colours: neutral slate with a muted steel-blue `brand` scale. | A19 | 26-11-2026 | **Demo mode** (`VITE_DEMO_MODE`): fake data and a one-click demo sign-in. With it off, the demo project list is empty. To be removed from production builds in Phase 34.              | 1     |
| A20 | 26-11-2026 | The Phase 1 demo session lives in the browser's sessionStorage and only decides what the UI shows. | A21 | 26-11-2026 | Base components are written in the shadcn/ui style by hand (Radix primitives + Tailwind + `cva`), not generated with the shadcn CLI, so they use our tokens directly.                                                                                                                                                                               | 1     |
| A22 | 26-11-2026 | Department URLs are short slugs (`/finance`, `/hr`, ...) and the project switcher's value is `?project=` (none = all projects, `company` = company-wide, otherwise a project id). Project ids can never be `all` or `company`.                                                                                                                      | 1     |
| A23 | 26-11-2026 | Sales is the only department limited to one project type (development). Admin has no project view. Every other department works with both contract and development projects.                                                                                                                                                                        | 1     |
| A24 | 26-11-2026 | A signed-out visitor to any unknown address goes to sign-in first; after sign-in, unknown addresses show "Page not found" inside the app. This avoids revealing which addresses exist.                                                                                                                                                              | 1     |
| A25 | 26-11-2026 | The phone app uses the platform's system font (no Inter download) to keep the app small; colours, sizes and spacing still come from the shared tokens. Body text is one step larger than on the web (17dp) for outdoor reading.                                                                                                                     | 1b    |
| A26 | 26-11-2026 | Site staff work on one site at a time, so the phone keeps a single **current site** instead of the web's All projects / Company-wide views.                                                                                                                                                                                                         | 1b    |
| A27 | 26-11-2026 | The Phase 1 mobile demo session is held in memory only: closing the app signs out. Phase 2 keeps the real session token in the phone's secure storage.                                                                                                                                                                                              | 1b    |
| A28 | 26-11-2026 | Mobile demo mode: `EXPO_PUBLIC_DEMO_MODE=true/false` forces it; unset means on in development builds and off in release builds. With it off, the demo site list is empty.                                                                                                                                                                           | 1b    |
| A29 | 26-11-2026 | Demo fixtures live in a separate entry point, `@erp/shared/demo`, so they are never pulled into the main shared library by accident; web and mobile both use it.                                                                                                                                                                                    | 1b    |
| A30 | 26-11-2026 | The mobile app can also be exported for the browser (`react-native-web`) so its screens can be reviewed without a phone. This is a review aid, not a supported way to use the app.                                                                                                                                                                  | 1b    |
| A31 | 26-11-2026 | Phone sessions end after 7 days without activity (30 days at most), because site staff can be offline for days; web sessions end after 30 minutes idle (12 hours at most). All four are settings (env now, company settings in Phase 4).                                                                                                            | 2a    |
| A32 | 26-11-2026 | **(access rules)** Sessions are stored on the server (random token, only its SHA-256 kept), not self-contained tokens, so a leaver's access ends on their very next request. Web: httpOnly, SameSite=Lax cookie on /api. Phone: Bearer token.                                                                                                       | 2a    |
| A33 | 26-11-2026 | Passwords: at least 12 characters, a block-list of common passwords, no repeated characters or simple sequences, no name/username/email; no forced symbols or periodic expiry (NIST SP 800-63B). Hashed with scrypt (N=2^17, r=8, p=1).                                                                                                             | 2a    |
| A34 | 26-11-2026 | 5 wrong passwords in a row lock the account for 15 minutes; during the lock even the right password is refused. Every sign-in failure (wrong password, unknown user, locked, leaver) gets the same message, so the API never reveals which accounts exist.                                                                                          | 2a    |
| A35 | 26-11-2026 | CSRF defence: every request that changes data must carry the `x-erp-client` header (web or mobile); CORS allows only our own web origins, so another site cannot add it.                                                                                                                                                                            | 2a    |
| A36 | 26-11-2026 | Until Phase 3, every signed-in user sees every department in the web app. The single provisional role on each user only decides who needs two-factor sign-in (2b) and who may manage users (2c).                                                                                                                                                    | 2a    |
| A37 | 26-11-2026 | Demo sign-in (one click, no password) exists only when the API runs with AUTH_DEMO_LOGIN=true, which the API refuses to start with in production; it accepts only the fixed demo usernames.                                                                                                                                                         | 2a    |
| A38 | 26-11-2026 | Sign-in throttling per network address counts FAILED attempts only (30 in 15 minutes by default), so an office signing in correctly behind one shared address is never blocked. It and the cap on concurrent password hashing (8 at once, 64 waiting) live in memory per API process; a multi-server setup would need a shared store (Phase 34).    | 2a    |
| A39 | 26-11-2026 | People may sign in with their username or their email address.                                                                                                                                                                                                                                                                                      | 2a    |
| A40 | 26-11-2026 | In the Docker stack the API is reached only through the web server (`/api`), not on its own port, so the client address nginx passes on can be trusted.                                                                                                                                                                                             | 2a    |
| A41 | 27-11-2026 | The local demo's one-click sign-in skips two-factor, so the demo can be reviewed without an authenticator app. Password sign-in in the demo still asks for it (demo.admin has it on with a demo secret; demo.director and demo.finance show the setup step).                                                                                        | 2b    |
| A42 | 27-11-2026 | **(access rules)** Two-factor uses standard authenticator-app codes (TOTP: SHA-1, 6 digits, 30 seconds, one step of clock drift either way). Each code works once. Ten one-time recovery codes (10 characters, about 50 bits each) are shown once at setup; only keyed hashes are stored.                                                           | 2b    |
| A43 | 27-11-2026 | Wrong two-factor codes count towards the same lockout as wrong passwords (5 in a row). Reaching it locks the account for 15 minutes and ends every session.                                                                                                                                                                                         | 2b    |
| A44 | 27-11-2026 | Authenticator secrets are encrypted with AUTH_ENCRYPTION_KEY (AES-256-GCM). Losing the key means everyone sets up two-factor again; the API refuses the published demo key in production. Key rotation is possible later (stored values carry a version).                                                                                           | 2b    |
| A45 | 27-11-2026 | After the right password, a user who still needs two-factor gets a half-signed-in session that can only finish two-factor (or sign out) and ends after 10 minutes. Finishing it always opens a new session with a new token.                                                                                                                        | 2b    |
| A46 | 27-11-2026 | Users in roles that do not require two-factor may switch it on (and off again) from Account security. Required roles cannot switch it off; an admin reset for a lost phone without recovery codes arrives in Phase 2c.                                                                                                                              | 2b    |
| A47 | 28-11-2026 | **(access rules)** A new starter in a role that requires two-factor changes the temporary password BEFORE setting up two-factor, so whoever issued the temporary password cannot enrol their own phone. Setup secrets belong to the session that asked for them.                                                                                    | 2b    |
| A48 | 28-11-2026 | **(access rules)** Switching two-factor on from an ordinary signed-in session, switching it off, and making new recovery codes all ask for the password again (on the same lockout counter). A role that requires two-factor is never fully signed in without it, even on a session opened before the rule (demo one-click sessions excepted, A41). | 2b    |
